Built to stay up

Restarting the panel never touches your traffic.

The control plane and the data plane are separate. Caddy, your apps and your databases keep running while Dockyrd updates, crashes or restarts.

  • Blue/green deploys. The new container must pass its health check before Caddy switches the upstream.
  • Self-healing. A reconciler compares what should run with what does every 30 seconds and repairs drift.
  • Signed updates. Releases are checksummed and cosign-verified, with automatic rollback if the new version fails to start.
  • Volumes are sacred. Nothing automatic ever deletes a volume. Only an explicit, confirmed delete does.

Introduction

Dockyrd is an open source, self-hosted deploy platform for a single server. You install one binary, open a dashboard and deploy apps, static sites, databases and storage buckets with automatic HTTPS.

Who it is for

Developers and small teams who want the Vercel or Railway experience on a VPS they control. If you run a handful of Next.js apps, a marketing site and a Postgres database for a client, Dockyrd is built for you.

The mental model

Everything in Dockyrd fits in four levels:

LevelWhat it isExample
ServerThe machine Dockyrd runs on. v0.1 manages one.local
ProjectA group of services with its own private network.Client X
EnvironmentA stage inside a project.production
ServiceSomething that runs or is served.app, static site, postgres, redis, bucket

Each change to an app or static site creates a deployment. Deployments are kept, so you can roll back to any of the last five without rebuilding.

Principles

  • Light. One Go process and Caddy. No Postgres, Redis or queue for the platform itself.
  • Stable. The panel can crash or update without a single request failing.
  • Safe by default. Databases are private, secrets are encrypted at rest, and a fresh install needs a one-time token.
  • Small UI. One consistent screen per service type instead of a wall of options.

Ready to try it? Read the requirements, then follow the quick start. A fresh install takes less than three minutes.

Install

Run this as root on the server:

curl -fsSL https://raw.githubusercontent.com/Joeydekruis/dockyrd/development/scripts/install.sh | sudo sh

The script will:

  1. Check the OS, architecture, ports and free disk space.
  2. Install Docker Engine from Docker's official repository if it is missing (version 27 or newer is required).
  3. Set log rotation and live-restore in /etc/docker/daemon.json, merging with what is already there.
  4. Download the binary, verify its checksum and signature, and install it to /usr/local/bin/dockyrd.
  5. Run dockyrd init, start the proxy and BuildKit containers and enable the systemd service.
  6. Open ports 22, 80, 443 and 8000 if ufw is active.

When it finishes you see a setup link:

✓ Dockyrd v0.1.0 is running.

  Open:   http://203.0.113.10:8000/setup?token=8f3k-29xq-a71m
  Token is valid for 60 minutes and can be used once.
  Lost it?  sudo dockyrd setup-token

Keep the setup link private. Whoever uses the token first becomes the owner of the instance. Without a valid token nobody can claim it.

Installer flags

curl -fsSL https://raw.githubusercontent.com/Joeydekruis/dockyrd/development/scripts/install.sh | sudo sh -s -- --version v0.1.2 --dashboard-domain dockyrd.example.com

First-time setup

Open the setup link and the wizard asks for three things:

  1. Owner account. Name, email and a password of at least 12 characters.
  2. Instance. An optional dashboard domain, the email used for Let's Encrypt, and an optional wildcard domain for apps.
  3. GitHub. Optional. You can connect a GitHub App now or later from Settings.

Uninstall

The uninstall script stops the service and removes the platform containers. It asks before touching your own containers, volumes or data, and keeps them by default.

curl -fsSL https://raw.githubusercontent.com/Joeydekruis/dockyrd/development/scripts/uninstall.sh | sudo sh

Deploy your first app

From an empty dashboard to a Next.js app with a Postgres database on its own HTTPS domain in about ten minutes.

1. Connect GitHub

Go to Settings → Git providers and choose Create GitHub App. Dockyrd uses GitHub's manifest flow, so you only confirm the app name and pick which repositories it may read. Push events start deploys automatically.

2. Create a project

Open Projects and create one, for example Client X. Every project gets its own private Docker network, so services in different projects cannot see each other.

3. Add a database

Inside the project, create a Postgres database and name it db. Dockyrd generates a 32-character password and starts it on the project network. Other services reach it at db:5432.

4. Create the application

  1. Choose Create application → GitHub and pick your repository and branch.
  2. Leave the builder on Railpack. It detects Next.js and sets the build and start commands.
  3. Under Variables, add a reference to the database:
DATABASE_URL=${{db.DATABASE_URL}}
  1. Choose Deploy and follow the build log live.

Your app is now reachable on a generated domain such as webshop-x7k2.203-0-113-10.sslip.io, with HTTPS.

5. Add your own domain

Under Domains, add webshop.example.com and point an A record at your server's IP. Choose Check again once DNS has updated; Caddy requests a certificate on the first request.

Done. Every push to the branch now deploys with zero downtime. If a build or health check fails, the previous version keeps serving traffic.

Next.js apps

Railpack detects Next.js automatically. A few settings make builds faster and images smaller.

Use standalone output

Set output: 'standalone' so the image only contains what the server needs. Dockyrd shows a hint on the app page when it is missing, but it is never required.

import type { NextConfig } from 'next'

const config: NextConfig = {
  output: 'standalone',
}

export default config

Public variables need a rebuild

Variables starting with NEXT_PUBLIC_ are inlined into the client bundle at build time. Dockyrd marks them as build-time automatically and shows that changing one triggers a rebuild, not just a restart.

Add a health check

By default Dockyrd waits until the port accepts connections. For a stricter check, set Health path to a route that returns 200 once the app can serve traffic:

export function GET() {
  return Response.json({ ok: true })
}

Builds on small servers

Next.js builds are memory hungry. On a 1 GB server the installer adds swap so builds finish, but they are slow. Use 2 vCPU and 4 GB if you build often, or build in CI and deploy the resulting image.

Static sites

Static sites build in a throwaway container and are served by Caddy straight from disk. No container keeps running.

Set Node version to none for plain HTML repositories without a build step.

Releases and rollback

Each deploy copies the output to its own release folder. A symlink called current is switched atomically, so visitors never see a half-written site. Rolling back moves the symlink back and takes milliseconds. The last five releases are kept.

Single-page apps

Turn on SPA fallback to serve index.html for unknown paths, so client-side routes work on refresh.

Environment variables

Variables on a static site are injected at build time only. Changing one starts a new build.

Databases

Postgres and Redis-compatible databases from official images, each with its own volume and generated credentials.

The Redis option runs Valkey, the BSD-licensed fork of Redis. It speaks the same protocol, so existing Redis clients work unchanged.

Connecting from an app

Databases publish variables that apps in the same project can reference:

DATABASE_URL=${{db.DATABASE_URL}}
REDIS_URL=${{cache.REDIS_URL}}

References resolve on every deploy, so rotating a password only needs a redeploy of the apps that use it.

Private by default

Dockyrd never publishes a database port. Databases are reachable only from services in the same project. Docker-published ports bypass ufw, so this default matters.

Backups

Scheduled database backups arrive in v0.2. Until then, run pg_dump yourself on a schedule. Dockyrd does back up its own control-plane database daily.

Object storage

Dockyrd can run Garage, a lightweight S3-compatible server, next to your apps for uploads and assets.

Install Garage

Open Object storage and choose Install Garage. Dockyrd starts a single-node Garage container, generates its secrets and stores data in /var/lib/dockyrd/garage.

Buckets and keys

Create a bucket inside a project. Dockyrd creates an access key for it and connects Garage to that project's network. Apps reference the credentials like any other service:

S3_ENDPOINT=${{uploads.S3_ENDPOINT}}
S3_BUCKET=${{uploads.S3_BUCKET}}
S3_ACCESS_KEY_ID=${{uploads.S3_ACCESS_KEY_ID}}
S3_SECRET_ACCESS_KEY=${{uploads.S3_SECRET_ACCESS_KEY}}

Public access

Buckets are private. Turn on Public read to serve files such as images through a Caddy route. For browser uploads with presigned URLs, expose the S3 endpoint on s3.<your-dashboard-domain> in Settings.

Why not MinIO?

The MinIO community edition stopped shipping binaries and images in 2025 and its repository is now archived. Dockyrd only installs actively maintained software.

Domains & HTTPS

Every app and static site gets a working HTTPS address immediately, and you can add your own domains at any time.

Platform domains

Without any DNS work, each service gets an address on sslip.io built from your server's IP, such as blog-a3f9.203-0-113-10.sslip.io. Set a wildcard domain in Settings → Instance, for example *.apps.example.com, to use your own.

Custom domains

Add the domain on the service's Domains tab and create the record shown:

Aexample.comYour server's IPv4 address
AAAAexample.comYour server's IPv6 address, if it has one
CNAMEwwwexample.com

Choose Check again to verify. Once DNS points at the server, Caddy gets a Let's Encrypt certificate and renews it automatically.

Redirects

Mark one domain as primary and redirect the others to it, for example www to the apex. HTTP always redirects to HTTPS.

Environment variables

Variables are set per service, encrypted at rest and can reference other services in the same project.

Build-time and runtime

Every variable can apply at build time, at runtime, or both. Secrets are passed to builds as BuildKit secrets rather than build arguments, so they never end up in image layers, and they are masked as •••• in logs.

References

Use ${{service.VARIABLE}} to reference a value another service publishes:

ServicePublishes
PostgresDATABASE_URL, PGHOST, PGPORT, PGUSER, PGPASSWORD, PGDATABASE

References only resolve within a project. Circular references are rejected when you save.

Paste a .env file

The variables editor accepts a pasted .env file and creates one variable per line. Revealing secret values is recorded in the audit log.

Updates

Dockyrd updates itself from signed GitHub releases. Your apps, databases and the proxy keep running during an update.

How updates are found

Dockyrd checks for a new release once a day. When one is available, the sidebar shows Update available. Applying it is manual by default; you can enable automatic installs for patch releases in Settings.

What an update does

  1. Downloads the release and verifies its SHA-256 checksum and cosign signature.
  2. Takes a snapshot of the control-plane database.
  3. Swaps the binary atomically and keeps the previous one.
  4. Restarts the service. Caddy and your containers are not restarted.
  5. Rolls back to the previous binary and database automatically if the new version does not report ready within 60 seconds.

The proxy only restarts when a release ships a new Caddy image. Release notes say so, and the restart takes about one second.

Update from the command line

sudo dockyrd update
sudo dockyrd update --version v0.1.3

Troubleshooting

Start with dockyrd doctor. It checks the usual suspects and prints a concrete fix for each problem it finds.

sudo dockyrd doctor

Certificate is not issued

  • Check that the domain's A record points at this server. The Domains tab shows the expected value.
  • Ports 80 and 443 must be reachable from the internet. Check your provider's firewall as well as ufw.
  • Let's Encrypt fails when the server clock is off. doctor checks this.

A deploy fails its health check

The previous version keeps running. Open the deployment to see the build and runtime logs. Common causes are a wrong port, an app that listens on 127.0.0.1 instead of 0.0.0.0, or a health path that needs the database before it is ready.

Builds refuse to start

Dockyrd refuses builds when less than 10% disk is free. Open Analytics → Docker cleanup to remove build cache, dangling images and old releases. Cleanup never touches running services or volumes.

Locked out

sudo dockyrd admin reset-password you@example.com
sudo dockyrd admin disable-2fa you@example.com

Architecture

Dockyrd separates the control plane from the data plane, so managing your server never interrupts what it serves.

The three parts

  • dockyrd runs on the host as a systemd service. It holds the API, the job runner, builds, the reconciler, metrics collectors, the updater and the embedded dashboard.
  • Caddy runs as the dy-proxy container. Dockyrd sends it a complete JSON configuration through its admin socket; Caddy validates it atomically and keeps the old one if the new one is invalid.
  • Docker Engine runs everything else. Each project has its own network, and only services with a public domain join the dy-edge network.

Desired and actual state

SQLite stores what should be running. Docker labels on every container, volume and network describe what is running:

dev.dockyrd.managed=true
dev.dockyrd.project=<project_id>
dev.dockyrd.service=<service_id>
dev.dockyrd.kind=app|database|redis|bucket|system
dev.dockyrd.deployment=<deployment_id>

Every 30 seconds, at startup and after each job, the reconciler compares the two. It restarts services that should run, removes leftovers from failed deploys, reloads the proxy if its config drifted and marks interrupted deployments as failed.

A zero-downtime deploy

  1. Build the image dockyrd/<service>:<deploy>.
  2. Start a new container next to the old one.
  3. Wait for a TCP connection and, if configured, a 2xx from the health path.
  4. Switch the Caddy upstream, move the internal hostname, and stop the old container after a 30-second grace period.

If the health check fails, the new container is stopped, its logs are kept and the old one stays live.

Why the binary runs on the host

One binary under systemd has the fewest moving parts. It reads host metrics from /proc directly, updates itself with an atomic file swap, and restarting it never restarts a container.

Sign-in

  • Passwords are hashed with argon2id.
  • TOTP two-factor with ten recovery codes. The owner can require it for everyone.
  • Optional GitHub sign-in through your GitHub App. It links to existing accounts; it never creates one without an invite.
  • Sign-in attempts are rate-limited per IP and per account.

Secrets and isolation

  • Variables, database passwords, S3 keys and the GitHub App key are encrypted with AES-256-GCM.
  • User containers never get the Docker socket and run with no-new-privileges and a memory limit.
  • Projects cannot reach each other's networks.
  • Every change is written to the audit log with user, target and IP.

Reporting a vulnerability

Please report security issues privately as described in SECURITY.md in the repository. We follow a 90-day disclosure policy.
